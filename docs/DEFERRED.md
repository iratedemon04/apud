## Structural & code-quality (raised 2026-08-02 in a code-quality review; user asked to park them here, none scheduled)
*(Verdict: the lower three layers — Marc.Core / Apud.Data / Apud.Sync — read senior-grade; the debt is concentrated in the UI layer and a few small consistency nits. None of these are bugs; all are deliberate "later".)*
- 2026-08-02 (structural): **`MainForm.cs` is 2,425 lines — the one real structural weakness (next-biggest source file is 621).** Classic WinForms God-object: it hosts the editor, search, sidebar, menu/command wiring, all dialogs, AND the sync orchestration. It's *contained* debt — the heavy logic lives in the tested lower layers, so this file is mostly orchestration + event plumbing — but it's where a new dev gets lost first and where there's essentially no unit testing. Fix = extract a few collaborators (e.g. a search controller, an editor host, a sync coordinator) purely for navigability; behaviour is already below `Apud.App`. Budget ~1 day BEFORE adding anything significant to the UI. **NOT caused by, and not fixed by, anything about the deliverable's size (see packaging note).**
- 2026-08-02 (code-quality): **SQL-construction inconsistency.** Almost every query is parameterised, but `RecordRepository.CountLinksTo` (RecordRepository.cs:411) interpolates the id straight into the string (`$"... auth_record_id = {authRecordId}"`). It's a `long`, so NO injection risk today — but it's the lone string-built query and the pattern invites a future copy-paste where the value is a string. Normalise it to a parameter so the codebase has zero string-built SQL. (The `FtsIndexer` interpolations are different and fine — they splice a compile-time column list, which can't be parameterised.)
- 2026-08-02 (code-quality): **005 timestamp uses `DateTime.Now`** (PushService.cs:130), local time and non-injectable, which makes `AutoFill` mildly time-dependent to test. If value-level assertions on 005 are ever wanted, thread a `TimeProvider`/clock seam. Low priority.
- 2026-08-02 (efficiency): **N+1 loads in the authority stages.** `PushService.AuthorityStage` calls `_repo.Load(authId)` once per linked field (PushService.cs:80); `RewriteLinkedBibHeadings` loads once per linked bib. A non-issue at catalogue scale (a handful of links per record) — do NOT change speculatively — but named so a pathological record with dozens of links isn't a surprise. Batch-load if it ever shows.
- 2026-08-02 (structural): **The FTS index and heading_index are kept in step by hand.** `RecordRepository.Update` must remember to call both `FtsIndexer` and `HeadingIndexer` in the right order (it does, and comments the ordering). It's a *manual* invariant, not a structural one — a future write-path that forgets a call would cause silent index drift with no compiler complaint. Correct today; consider funnelling all record writes through one choke-point that maintains both indexes so it can't be forgotten.
- 2026-08-02 (feature, offered-not-built): **Reciprocal "used for" tracing** — standing on an authorized 1XX in the Ctrl+F4 browse does not list its 4XX variants. Traversal today is one-directional (variant → authorized, the direction cataloguing needs). Add if the full syndetic card (authorized heading + its see-from tracings) is wanted in-app; `heading_index` already has the rows, keyed by `auth_record_id`.
- 2026-08-02 (feature, decided-not-needed): **Reference-aware search inside Apud's OWN search box** (type a cancelled/variant form → get redirected to the authorized heading + its bibs). Confirmed 2026-08-02 this is NOT needed: the patron-facing see-from redirect is the discovery layer / OPAC's job, and Apud already authors + preserves + exports the 4XX tracings that power it (they travel in the AUT `.mrk`). Only build this if the *cataloguer* wants the redirect in Apud's own search while cataloguing — then: match the query against the `see` rows in `heading_index`, and on a hit show a "Historia de México — see: México--Historia" banner that re-runs on the authorized form. Modest add; not scheduled.
- 2026-08-02 (packaging, → Module 12 decision): **The published deliverable is ~169 MB, and it is NOT the code — it's the bundled .NET 8 runtime + the whole Windows Desktop framework.** Self-contained publish copies a private runtime in; the `Microsoft.WindowsDesktop.App` pack is indivisible so it drags ~30 MB of WPF (`PresentationFramework/Core`, `D3DCompiler`) that Apud never uses, plus BouncyCastle (~7 MB) from SSH.NET. Levers, ranked: **(1)** framework-dependent publish (169 MB → ~2–5 MB) requiring the .NET 8 Desktop Runtime on the target — the Module 12 Inno Setup installer can detect + chain-install it; the standard professional path. **(2)** self-contained + `PublishSingleFile` + `EnableCompressionInSingleFile` (→ ~90–100 MB, slower cold start, zero runtime dependency) for a copy-paste-portable exe. **(3) Trimming (`PublishTrimmed`) is RULED OUT** — officially unsupported for WinForms/WPF, breaks reflection at runtime. (4) ReadyToRun makes it bigger, not smaller. This is a real fork to decide at Module 12: smallest+installer vs portable+self-contained.

- 2026-08-02 (11) — **DEFERRED by user decision (build incremental + warning now, park parallelism)**: per-record `.mrk` upload is sequential, one connection. Measured ~10-13 ms/file; a huge FIRST backup is slow (~30 min parallel / ~90 min sequential at 500k). Incremental upload (per-folder `.manifest` of filename→SHA256) makes every LATER backup send only changed records, so parallelism buys nothing in daily use — only a large first sync. Not built: an N-connection parallel uploader (would be the codebase's first concurrency; the `Func<ISftpTransport>` factory already supports multiple connections, so it can be added in isolation). Large first backups are instead covered by `BackupTimeForm` (Help → Backup Time). True "500k in minutes" would need archive-upload + server-side extract, which crosses the SFTP-only design law — separate decision if ever needed.
